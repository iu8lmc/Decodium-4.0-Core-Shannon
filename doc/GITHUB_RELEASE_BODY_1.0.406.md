# Decodium 4 FT2 1.0.406

Release 1.0.406 keeps the 1.0.405 FT8 low-thread compatibility fix and adds a second, more precise protection for users whose PCs enter an FT8 live decode backlog. The goal is to stop the "no decode or almost no decode" condition reported by some users from 1.0.396 onward, without removing the high-yield FT8 work used to close the JTDX gap on faster machines.

## Changes from 1.0.405

- FT8 live backlog guard:
  - Added detection for stale pending FT8 work in the live dispatcher.
  - When the worker is clearly behind, Decodium now drains queued FT8 early/deep requests and keeps the current final pass as the useful decode for the slot.
  - The guard is conservative: it triggers only when pending FT8 work is old enough or the live queue is visibly overloaded.
  - Added the diagnostic marker:
    `FT8 live backlog drain`
    with the kept serial, removed metadata count, cooldown and backlog reason.

- FT8 deep/AP behavior preserved on fast PCs:
  - If the PC is keeping up, the normal 1.0.405 path remains active.
  - Fast machines still use the full split pipeline: fast pass plus deep/AP follow-up.
  - No JTDX-gap recovery logic, hash cache size, weak-signal candidate logic, filters or deduplication has been removed.

- Slow/constrained PC behavior:
  - When backlog is active, optional early/deep work is temporarily skipped so results do not arrive one or more slots late and get discarded as stale.
  - The deep follow-up cooldown is used only as a pressure relief mechanism.
  - Slow PCs may decode fewer weak signals than fast PCs, but should no longer remain stuck for minutes with stale serial callbacks and no visible FT8 output.

- FT8 hash/log seeding path:
  - Initial local log/hash seed collection now runs asynchronously instead of blocking the live FT8 decode worker.
  - Recent-log context refresh is also collected asynchronously and applied only when ready.
  - This removes a blocking path seen in user logs where the first FT8 decode spent tens of seconds before the native decode stage.

## Evidence from user logs

The diagnostic logs showed healthy audio capture but FT8 callbacks arriving with old serials and then being ignored by the UI as stale. In one run the first FT8 metrics showed very high total time with almost no native decode time, pointing to live-path preparation/backlog rather than RF/audio failure. Later in the same log, Decodium was dispatching current FT8 serials while receiving results from much older serials.

This release addresses both parts:

- the log/hash preparation no longer blocks the worker synchronously;
- the Bridge drains stale FT8 live work when the queue is already behind.

## Timing

- The fix does not increase the FT8 late-decode delivery window.
- Fast-path timing remains bounded by the existing final and follow-up budgets.
- On overloaded PCs the scheduler prefers a timely final decode over late optional deep passes that would be discarded by the UI.
